# 项目定位与价值解读

帮助读者理解“这是什么，为什么值得存在”，而不是把 README 或技术架构换成更简单的措辞。

## 解读路径

围绕读者的疑问组织回答，不必机械凑齐章节。初次介绍可沿着以下逻辑展开，追问时只解释新增疑点：

- **它是什么**：先说明软件类别和承担的角色。例如区分完整应用、插件、接口协议、模型和服务。用“谁在什么情况下，用它完成什么事”解释，必要术语随用随解释。
- **具体场景**：用一个贯穿的小例子说明输入、做事过程和最终产物；对照原来的办法，避免只给抽象定义。
- **没有它怎么办**：找现实中最接近的既有方案，包括已有产品、脚本/API、插件/MCP 封装以及简单手工流程。比较同一个任务，而不是挑选明显不适合的对手。
- **它带来什么变化**：区分新增能力、部署/成本/体验/集成上的改进、实现方式差异和已有方案的共性。价值不只等于技术原创，但每项优势都要有依据。
- **谁需要、谁不需要**：给出适用条件、替代方案已经够用的情形、成熟度和实质局限。可以得出“有探索价值，但不是完成此任务的必需品”，也可以得出某个场景中确有优势；不要预设赞扬或否定。

## 证据与比较

- 优先核对项目官方说明、文档、示例和必要的源码；比较对象也查官方资料。只为核实关键疑点查看源码，不把回答变成代码结构报告。
- 区分**项目宣称、证据支持的能力、作者明确说明的动机、自己的推断**。作者未说明为什么重写时，不替作者编造理由。
- 宣称“独有”“更稳定”“更快”“更适合 AI”“更省 token”前，核查替代方案与测试条件；没有证据时明确是设计目标、可能收益或尚待验证。
- 对共享核心、API、自动化、参数化、开源、某种语言实现等，先确认是否行业常见，不能直接包装成竞争壁垒。也不能仅凭相同功能就断言两者体验和可靠性相同。
- **接口层与执行层分开讲**：接入 MCP 不等于新增几何/业务能力；脚本和界面可调用相同核心，也可能分别走命令与数据 API。不把“脚本入口不同”误说成“另写了一套底层逻辑”。
- 功能清单、架构图、演示和星数不能单独证明生产可靠性；同一任务的成功率、操作成本、恢复能力等有数据才比较，无数据就保留结论。
- 来源访问失败时说明验证范围，不补造事实。用户指出已有方案也能做到时，先核实并直接修正原判断，不转移到新的宣传点。

## 表达与边界

- 默认简洁中文 Markdown，先给直白结论，再用例子解释；引用紧邻关键事实。除非用户要深入，不堆技术栈、crate/文件名、命令、安装步骤或底层原理。
- 始终站在“现有工具不是也能做到吗，为什么还要它？”的读者角度，但不用抬杠式语气，也不默认项目一定不可替代。
- 默认在对话中回答。仅在用户要求网页、笔记或文件时创建对应产物；产物仍以场景、替代方案和存在意义为主，不能因换成 HTML 就退回架构展示。
- 本 skill 不授权安装软件、修改配置、编辑已有笔记或部署项目。用户明确要使用教程、架构或代码分析时，按那一请求处理，不把价值解读强加进去。

## 输出前自检

读者能否说出：它属于什么工具、实际能做什么、以前怎么做、相比之下到底变了什么、自己是否需要？

如果答案只剩“新语言实现 + 支持 AI + 一张架构图”，还没有完成项目解读。
